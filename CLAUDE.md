## WHAT — Stack
- Rust (latest stable, edition 2024) — single statically-linked binary
- TUI: `ratatui` + `crossterm` (task tree browser with live command output)
- Target: Linux servers, multi-distro (Debian/Ubuntu, RHEL/Rocky/Alma, Arch, Alpine and openSUSE/SLES implemented)
- Database: none — state lives in the host system itself. The one file this tool keeps is `/var/lib/initd/backups.jsonl`, an append-only record of *where a copy of a changed file was put*; see the WHY entry on it.

- Runtime: Rust latest stable via `rustup` (1.95.0 at bootstrap, 2026-04), edition 2024

## WHAT — Structure
- `src/main.rs` — entry point: dispatches to TUI (no args) or CLI subcommand
- `src/error.rs` — domain error type; carries structured data only, never display text
- `src/i18n/` — message catalogue + locale resolution (dependency-free; every user-facing string goes through it)
- `src/distro/` — `/etc/os-release` detection and family resolution
- `src/backend/` — one module per distro family (`debian`, `rhel`, `arch`, `alpine`, `suse`), each resolving the names a capability has there, plus the implementations they share: `systemd`, `systemd_user` and `openrc`; `unix_files`; `unix_accounts`, `shadow_accounts`, `busybox_accounts` and `posix_accounts` (what the two account suites do identically); `nftables` and `firewalld`; `procfs_sysctl`; `semanage`; `rpm_repositories` and `apt_periodic`; `wg_tools`; `release_installer`
- `src/domain/` — capability traits: packages, services and user services, files, account reading and writing, firewall, sysctl, WireGuard, verified binaries, SELinux, package repositories, automatic updates
- `src/tasks/` — the task tree exposed by the TUI (each task is typed Rust, declares supported distros)
- `src/tui/` — navigation and state in `app.rs`, drawing in `render.rs`, execution output pane; `signals.rs` catches the dropped connection and `verify.rs` runs the window that a silent session reverts
- `src/exec/` — `Executor` trait + `LocalExecutor` (the single choke point for running commands), `MockExecutor` and `PrivilegeEscalator`
- `tests/` — integration tests
- `docs/` — portable contract (see below)

## WHAT — Distribution
- Distributed as a static musl binary via **GitHub Releases** (x86_64 + aarch64).
- Bootstrap install is a one-liner in the linutil style: `curl -fsSL <url> | sh`, where the script downloads the release binary and **verifies its checksum** before executing.
- No deployment target, no hosting, no reverse proxy — the tool runs *on* the server being administered.

## WHAT — Task areas

Fifty-two tasks across six areas: identity and access, remote access (SSH and WireGuard), network (firewall and kernel parameters), services (containers, web server), the developer environment, and hardening. ## WHY — Architectural decisions

- **Distro differences are resolved by a per-family backend behind a trait, not by conditionals inside each task.** Detection reads `/etc/os-release` once at startup and resolves a backend (Debian/RHEL/Arch/Alpine/SUSE). Tasks call the trait and stay distro-agnostic. Adding a distro must mean adding one module, never editing every task — with N tasks, per-task branching would repeat the same `match` N times and each new distro would touch all of them. The one place a family is named outside a backend is `Task::support`, and that is deliberate: whether a task *runs* on a family is a decision, not a spelling, and the thirteen refusals in the tree each cite something measured — which repository has never carried fail2ban, which shipped `Include` wins on RHEL, which installer publishes no digest. It returns `Support` from an exhaustive `match` rather than a list of families, so a new variant fails to compile in every task that has not decided about it; the thirty-five that work everywhere say so through `supported_everywhere!`, written once, and only the fifteen with something to explain write the match out. Measured rather than assumed: adding a fifth family produced **34** compile errors naming exactly the sites that must answer — this file predicted 31 before SUSE was built, and 34 is what it cost — where the previous `&[Family]` produced none and left the new distribution silently unsupported.

- **A family can disagree with the trait, and SUSE is where that was measured rather than assumed.** The claim above — one module per distribution, never a task edited — held for RHEL and holds for most of SUSE: twenty tasks were covered by `supported_everywhere!` in one line, and the fifth family produced **34** compile errors naming exactly the sites that had to decide (this file predicted 31; the prediction was the estimate and 34 is the measurement). What it did not survive is `admin_group()`. Four families treat "in the administrative group" and "can escalate" as one fact, which is why the method returned a name and the name was the whole answer. openSUSE ships `%wheel` **commented out** in `/usr/etc/sudoers` — verified as the distribution's default rather than an artefact of the image, since `rpm -V sudo` reports the file unmodified on both variants — so `usermod -aG wheel` succeeds, membership reads back true, and the account still cannot escalate. Both callers were harmed differently: `users.create` would report an administrator it did not make, and `users.lock-root`, whose entire purpose is refusing to lock root while nobody else can administer the machine, would have **approved on a reading that is true and irrelevant**. So the trait grew `admin_group_grants_alone` and `grant_admin`, defaulted so the other four are untouched. The honest summary is that the design's promise is about *tasks*, not about the trait beneath them: a distribution that merely renames things costs one module, and one that disagrees about what a name *means* costs a method. **The distinct error is half the fix:** reporting `NotAnAdministrator` would send an operator to `usermod` for something `usermod` cannot repair, and assert a membership the system contradicts — so `AdminGroupGrantsNothing` names the file and the line to uncomment. Two more findings came with it. The `/usr/etc` split leaves `/etc/ssh/sshd_config` **absent** on a fresh host while sshd runs fine, and five SSH tasks read that path before editing it — fixed once in `ensure_config_present` rather than five times in the tasks, which is the shape of change where the sixth is the one that forgets. And openSUSE carries RHEL's crypto-policies mechanism yet `ssh.harden-strict` is supported here where RHEL refuses: the shipped config Includes `/etc/ssh/sshd_config.d` on line 12 and its own drop-ins on line 18, and sshd honours the first occurrence — measured against a daemon, `Ciphers aes256-ctr` written the way the task writes it came back from `sshd -T`.

- **A family is not guaranteed to speak with one voice.** Every backend before this resolved one set of names, because a family was assumed internally consistent. Tumbleweed packages Zellij and Leap 16.0 does not, so `SuseBackend::for_distribution` resolves a distribution — the mechanism `RhelBackend` already used for Docker's repository paths, reached here for a second and unrelated reason, which is what makes it a pattern rather than a one-off. The consequence for tests is that SUSE is the one family carrying **two** images: a matrix holding only the rolling variant would have agreed with the backend about a name the stable one does not have, and `EXPANDED` therefore asserts `suse` twice rather than deduplicating.

  **The same two images have now collided twice, in two different files, and the second time the fix for the first was already written down.** `Image::family_tag` exists because committed images were named after `image.family` — which answers `suse` for both — so Tumbleweed and Leap shared one cached image and whichever ran second silently exercised the other's packages. Its doc comment says exactly that. `TwoHosts::start` then named its *containers* the same way, and because `start` begins by tearing down leftovers under those names, the second scenario to start **deleted the first's containers while its test was still running**. CI reported it as `ssh.harden must not lock out an old client (client Error response from daemon: No such container …)` — the tier under test blamed for containers another test removed — after the survivor waited its full 180s for a server that no longer existed. Measured: 207s and a failure, against 13s and a pass once the name included the image. The lesson is not "use `family_tag`", which was already known; it is that a fix recorded as a comment on the helper it fixed does not reach the next place with the same shape. Anything naming a *resource* after a family has to ask whether that family has one image or two — and `image.family` remains right for messages and assertions, which is what it is for.

- **A capability is one name for one job, and Docker was one name for two.** `docker-rootless.install` installed an engine *and* set it up for an account, so `Capability::DockerRootless` had to resolve a single package name for both — and on three of five families the name it resolved was wrong. Measured rather than reviewed: `docker-ce-rootless-extras` declares `Enhances: docker-ce`, **not `Depends`**, so `apt-get install -s` on `debian:13` brings in `rootlesskit` and the two scripts and **no daemon and no client** — a rootless wrapper around an engine nobody installed. Arch was worse: **no official package ships `dockerd-rootless-setuptool.sh` at all** (`pacman -F` finds only `extra/rootlesskit`), so the task ran a script that does not exist, while a comment in `arch.rs` asserted the opposite. openSUSE keeps the script in `docker-rootless-extras`, which the task never installed. And Alpine was excluded from Docker entirely on the grounds that it packages none — it packages **both** (`docker-29.5.2-r0` and `docker-rootless-extras`); what it lacks is a per-user service manager, which is a fact about OpenRC and belongs in `Task::support`, where the refusal can say so. The split is therefore not tidying: `docker.install` is the machine's, `docker.rootless` is one account's, and the second refuses when the first has not run rather than installing a system daemon from a task asked about one user. **"The official way" is not one thing.** Docker publishes a repository for six platforms and Arch, openSUSE and Alpine are not among them, so the official route there is the distribution's package — which is exactly what a per-family backend is for. **What made all four survive is the shape worth remembering:** the only container coverage Docker had was a *refusal* (`user=nobody`), so every one of these passed the suite for as long as it shipped. A scenario that reaches the install found two more the same afternoon — RHEL's `baseurl` was missing `$releasever/$basearch/stable` and resolved to the archive root (404 against 200, measured), and `register` assumed `curl` and `gpg` on a `debian:13` that has neither, reporting a good key as unreadable. A test that only asserts what a task *refuses* proves nothing about what it *does*.

- **Tasks are native typed Rust, not embedded shell scripts.** linutil (the inspiration for this tool) embeds `.sh` files described by TOML. That is faster to contribute to but gives up type safety, testability, and compile-time checking, and inherits every difference between distro shells. Since the real value here is the distro abstraction, tasks must be able to *call* it — a shell script cannot.

- **All command execution goes through the `Executor` trait, even though only `LocalExecutor` exists.** The tool runs on the machine it administers, so local execution is the only implementation needed today. The trait exists so that remote execution (SSH) can be added later as a second implementation. Without it, `std::process::Command` calls would spread across the codebase and adding a transport layer would mean touching every call site. Cost of the indirection now: one layer. Cost later: a full refactor.

- **Privileged commands hand the terminal over; the password is never captured by the TUI.** `sudo` prompts on the TTY, but raw mode disables echo and line buffering and the alternate screen hides the prompt, so the TUI leaves both before spawning and restores them after — the pattern ratatui documents for spawning an external editor. The final `clear()` is required, not cosmetic: programs that query terminal colours otherwise leave raw ANSI RGB values printed inside the restored interface. **Rejected for the escalation password:** reading it into a masked TUI field and piping it to stdin. It would hold it in process memory, and `sudo` requires a TTY by default — the second half is decisive, since the field would not work at all. Note `run0` authenticates through polkit and isolates its own prompt, but it is a symlink to `systemd-run` and does not exist without systemd — which is why the mechanism is resolved at runtime rather than assumed.

  **The one exception is `users.create`'s password field, and the difference is what the alternative was.** For `sudo` the alternative is handing over the terminal, which is strictly better: the value never exists here. For a password being *set* on a new account there is no such option — `passwd` cannot be optional without a second field asking whether to run it, and that field was built, shipped, and asked an operator to type the word `yes` to answer a question with two answers. The value is therefore held, once, in a masked field, and applied through `chpasswd` on stdin — never `useradd -p`, whose argument `/proc/<pid>/cmdline` publishes to every account on the box. What the design still guarantees is enforced by tests rather than by intent: it is never drawn (`a_password_is_never_drawn_on_the_screen`), and it reaches no `argv` and no rendered line (`a_password_travels_on_stdin_and_never_in_the_arguments`), because `Command`'s `Display` omits stdin. The CLI cannot offer that guarantee — `password=` there is an argument of `initd` itself — and `docs/cli.md` says so rather than leaving it implied. **How long it is held was the part nobody had measured.** The interface keeps the values a task ran with so it can report what that task invalidated, so a password outlived its task by however long until another one replaced it — the whole session on a host where an account is created and nothing else. `finish_run` now overwrites and drops the secrets, on the failure path too, since a task that failed held the same value and reported nothing that needed it. What this does *not* claim is that the value is gone from memory: four other copies are made on the way to `chpasswd`, and a growing `Vec<char>` leaves fragments of what was typed — measured, twenty-eight characters reallocate three times and the largest abandoned block holds sixteen of them. Those are all short-lived. Removing the one copy that was not is worth doing; claiming the rest were handled would be the more dangerous half of the same change, and a `zeroize` dependency threaded through five layers would buy that claim for a threat model that already requires reading a root process's memory.

- **Authenticating once at startup is the fast path, not the only one, so the executor asks before a helper prompts rather than after it has.** The startup `sudo -v` covers the common case, and covers nothing else: Arch expires its timestamp after five minutes (measured, `tests/fixtures/validate-sudo-*.sh`) and a long task outlives it, while `doas` and `run0` have no timestamp to establish at all — on an Alpine box carrying `doas` and no `sudo`, the *first* privileged command is already the one that prompts. What that looked like was reproduced rather than reasoned about: a prompt raised under the interface is written into the alternate screen in raw mode (`\x1b[?1049h[sudo] password for …`), unreadable and unanswerable, so the interface appears to hang. So `LocalExecutor` asks `PrivilegeEscalator::auth_need()` before every privileged command — `sudo -n -v`, `doas -n true` and `run0 --no-ask-password true` each answer without raising a prompt, and only an unrecognised helper answers `Always`, because guessing "will not prompt" is the direction that strands someone at an invisible prompt — and when a prompt is coming it requests the terminal through a `TerminalBroker`. `run0` was assumed unprobeable at first on the grounds that polkit owns its prompt; measuring it on an Arch container with systemd as PID 1 and polkit running showed `--no-ask-password` refuses rather than asks, exiting 1 as an unprivileged user and 0 as root. Both conditions were needed to learn that: without them `run0` cannot reach the bus and every answer looks alike. **Detecting the failure afterwards was rejected:** `doas` without `persist` does not fail, it blocks on a prompt nobody can see, so there is no failure to detect; and matching sudo's stderr means matching another program's user-facing text. **Re-running the task after an auth failure was rejected too:** tasks are not idempotent, and one that got halfway would double-apply. The obligation this creates is that *whoever drains the channel must answer the request* — a caller that only reads it leaves the task thread blocked until the deadline, which a worker test now stands in for the interface to pin.

- **A task is stopped between two commands, and the flag reaches it through the executor rather than through `Task::run`.** Cancellation has to be cooperative because tasks are not idempotent: one killed mid-command leaves the step it was performing half applied, and there is no way to know which half. So `LocalExecutor` refuses the *next* command rather than interrupting the running one, which is the granularity the interface already promises. Routing it through the executor is what keeps the obligation off the fifty tasks — a token threaded through `Task::run` would have to be checked in each of them, and the one that forgot would be the one that could not be stopped. The check precedes authentication, so a stopped task does not go on to ask for a password. **Reporting the intent was rejected:** the request lands between commands, so a task already on its last one finishes, and a status row saying `CANCELLED` over a completed task is how a fully-configured server gets called half-configured — and re-run. The status now names the command the task stopped *before*, and a task that beat the keypress is reported as done with the near miss said out loud.

- **Losing the session counts as not confirming, which is the case the verification window exists for rather than an edge of it.** The countdown lived only in this process, so `ssh.harden` severing the administrator's own connection killed the interface with `SIGHUP` and left in place the very configuration that locked them out — the screen having promised that silence would restore it. `SIGHUP` and `SIGTERM` are caught, and the handler only raises a flag the event loop already polls every hundred milliseconds: a handler may touch only async-signal-safe things, and reverting spawns `cp` through an executor that takes locks, so doing the work there risks a deadlock against the code it interrupted. **`SIGKILL` and a power cut cannot be covered by any program**, so the banner states the limit — "Reverts while this session lives." — rather than implying otherwise: a promise with a silent exception teaches people to disbelieve the whole banner, which costs the warnings beside it too.

- **An undo that outlives its session needs a record, and the record is not a database.** The verification window undoes a change inside the session that made it — `.initd.bak` beside the original. Nothing recorded which task wrote that copy or when, so a second write replaced it silently and an operator returning next day held a file of unknown age. `/var/lib/initd/backups.jsonl` answers one question — *is there a copy of how this file looked before initd touched it, and where* — and nothing else may go in: `PermitRootLogin` is still read from `sshd_config`. Append-only is the whole locking story, since a half-written final line is invalid JSON and is discarded, where rewriting in place needs a lock and a lock needs a stale-lock story on a machine that reboots underneath it. **Restoring across sessions checks what restoring within one need not:** a day later the file may have been edited by hand, and putting the copy over that discards somebody's work while reporting success — so the live file is hashed against what this tool wrote and the copy against what was recorded, and either mismatch refuses. "Could not be read" is a separate error from "changed", because the two call for different actions. **Two tasks record nothing by decision, and one file is never copied at all.** `ssh.authorize-key` records nothing because its restoration *removes* an authorised key. `wireguard.add-peer` records nothing because `wg0.conf` holds the server's private key and every peer's preshared key. For that file the guarantee had a hole in it for as long as it existed: skipping the index does not skip the *sidecar*, so `write` went on leaving `wg0.conf.initd.bak` beside the original, and `prune` only ever reaches copies the index names. The comment said no copy was made while a copy was being made, and the test named for the property asserted only that no command mentioned `/var/lib/initd` — which the sidecar in `/etc/wireguard` passed without difficulty, its own mock already carrying a reply labelled `// backup`. **The rule that replaced it is the path rather than the moment:** every write to `wg0.conf` refuses to copy, in `install` as well as `add-peer`. That second one only surfaced in a container, and only because the scenario listed the directory rather than testing one name: `install` writes the file twice so the mode precedes the key, and on a host where a first run failed — Alpine's fails at `rc-update`, having written the key — the copy left behind was the whole configuration. Measured on `alpine:3.23`: 0 bytes after the install, 151 after the next task touched the path. The two mode bugs this shipped with — a `0755` parent, a `0644` index — were found the same way, on `debian:13` and `alpine:3.23`: a umask is a thing only a filesystem has, and so is a file nobody deleted.

- **`sshd -t` approves configurations nobody can connect to, so hardening is measured by a real login.** Validation parses the file; it cannot say whether a client and this daemon agree on a cipher, a key exchange and a MAC. A daemon given `Ciphers 3des-cbc` alone passes `sshd -t` and refuses every client — verified in a container. That is the failure `ssh.harden-strict` is documented as the only tier able to cause, so `tests/integration_connection.rs` starts a daemon and authenticates against it, and `tests/integration_old_client.rs` does so from an OpenSSH 8.4 client against a 10.x server, since an algorithm the server now insists on is one an older client may never have learned. Two harness details are load-bearing and were each found by a test failing for the wrong reason: the daemon must be started *after* the configuration is written (the tasks reload a unit that does not exist in a container, and a daemon started first stops listening), and the login must not be root (`ssh.harden` writes `PermitRootLogin no`, so a root session is refused by design).

- **`docs/cli.md`'s exit-code contract is verified against the binary, because it exists for automation rather than for readers.** A script that retries on `1` and gives up on `2` depends entirely on the difference, and nothing checked that the two stayed distinct. `tests/integration_shared.rs` walks every documented case; it was confirmed to catch a violation by introducing one, rather than assumed to. The lesson alongside it: an exit code alone can misidentify *why* something failed — port 1 exits non-zero in a container with no `sshd_config` to edit, which reads as the range check rejecting a valid port until the message is read. Assert on the message when the code has more than one possible cause.

- **A container test may only invoke tools present in every base image, and the failure mode is a test that lies rather than one that fails.** `diff`, then `cmp`, then `pgrep` each turned out to be missing from one of the two images. A missing comparison tool reports "differs", which failed the revert scenario whose revert had worked *and* passed the keep scenario, which asserts the files differ; a missing `pgrep` turned a wait-until-listening loop into a fixed thirty-second sleep that happened to be long enough. Substituting one tool for another repeated the bug twice, so the rule is to prefer what coreutils guarantees (`sha256sum` over `cmp`) or a condition the program itself produces (sshd's pid file over a process lookup), and to check any new tool against both images before relying on it. Where a helper does the comparing, pin it with its own scenario: a comparator that is wrong in either direction is invisible in the scenarios that use it.

- **The same rule again, at the layer below, found by adding two images rather than by review.** `exit_code_of` was fixed; `run_in_container` beneath it was not, and it hands back whatever Docker produced without asking whether a container ran. A daemon that cannot start one exits **125** with empty stdout, and empty stdout is what a scenario whose assertion legitimately failed also sees — so sixteen SUSE scenarios reported the backend as broken when the host had simply run out of memory. The trigger is arithmetic rather than a defect in the new family: nextest sizes parallelism by cores, this host has 32 of them and 15 GB, and openSUSE's images are large — four images fitted and six did not. Both container helpers now panic on 125 naming the image and both streams, and the guard is pinned in both directions, because one that also swallowed a script's own non-zero exit would turn the failures several scenarios assert on into panics about the harness.

- **The remedy that guard recommends was wrong, and the guard is what proved it.** Its panic said to re-run with `--test-threads 1`, and this file repeated that as the answer for six images on a host with more cores than memory. Measured rather than reasoned about a second time: a live container is **4.7 MiB** against **13 GB free**, and sixteen simultaneous starts of the largest image — `opensuse/tumbleweed` — fail **zero** times. Memory was never the constraint. What produced the original 125s was the daemon: Docker on WSL2 intermittently refuses every start with `failed to create shim: unsupported protocol: Yunix`, which a `wsl --shutdown` clears and no amount of serialisation does. The two look identical from inside a test — both are exit 125 with empty stdout — which is exactly why the first diagnosis stuck. The cost of believing it was **97 minutes against 8m57s**, an eleven-fold tax on every full run, paid for a year by whoever read this file. The lesson is narrower than "measure": the guard *did* its job both times, naming the image and the streams; what it got wrong was the advice appended to a correct observation, and advice is the part nothing tests. A panic may say what it saw. It should be slower to say what to do about it. **The same trap caught the fix for this one, which is why it is worth writing down twice.** `TwoHosts::start_server_daemon` waits for sshd by polling `/run/sshd.pid` and, when the poll runs out, returns as though the daemon were up — the silent-degradation shape this file condemns in two other places. Making it panic instead broke three scenarios that had been passing, because **openSUSE's sshd never writes that file** (measured on Tumbleweed and Leap; Debian's does). The silence was load-bearing: by the time the poll gave up the daemon had been listening for a minute, so the wrong mechanism and the missing check cancelled out. Left as it was, deliberately, until CI collected on it: `an_old_client_survives_the_safe_tier::tumbleweed` failed on a loaded runner, reporting `ssh.harden must not lock out an old client (client , server )` — the tier blamed for a daemon that had not finished starting. **The fix is the daemon's own words.** `sshd -D -e` prints `Server listening on ...` when it begins accepting, the harness already redirects that to `/tmp/sshd.log`, and `grep` is in all six images; the wait now polls for that line and the ceiling is **a hundred and eighty** seconds rather than thirty. It was ninety first, and ninety was wrong for a reason already written down beside it: the same paragraph recorded openSUSE taking 111s and 118s, so the ceiling was set below a number this file had measured. Two full runs at `-j8` collected on it, at 111s and 122s, and each time the scenario reported `ssh.harden` locking out an old client rather than a daemon still starting. Measured against those: the same scenario alone takes **14.9s**, a seven-fold spread that is contention and not the tier under test. The lesson is not "measure" — the measurement was there — but that a constant chosen beside a number must be checked against it. **`/dev/tcp` was the obvious choice and is wrong for exactly the reason the missing-`diff` finding teaches** — it is a bash extension, and Debian's `dash` and Alpine's busybox `ash` do not implement it, so both answer "not listening" forever; measured before it shipped rather than after. `ss`, `nc` and `netstat` are each present in exactly one of the six, and `ssh` is absent from Rocky, which installs only `openssh-server`. The timing question stays unanswered — openSUSE still takes 111s and 118s where the others take ten — but it is now a slow wait rather than a wait for something that never happens. The empty `(client , server )` in that failure was a second defect found by reading it: `ssh -V` prints on **stderr**, and both version helpers read only `stdout`, so the two versions a scenario exists to compare had always been blank.

- **What a container test costs is decided before it runs, and for dnf that cost is 69 MB.** The suite took seventeen minutes and the reason was not the work the scenarios do. Measured inside `rockylinux:9`: `/var/cache/dnf` is 4 KB on the bare image and **69 MB** after one `dnf install`, which is a solv cache built once — the second identical call takes 200 ms against 6551 ms, with the `.solv` mtime unchanged, so nothing is rewritten. A suite that discards the container per scenario rebuilds that cache every time. The three costs, per scenario: **6551 ms** bare, **2199 ms** on the metadata-only image `cached_image` already committed, **313 ms** with the packages baked in. So two thirds were already being recovered and the last third was the one nobody had taken; baking brought the full run from 1044s to 564s with the images deleted first. **Three obvious mitigations were measured and are wrong**, which is worth recording so they are not tried again: `fastestmirror` is already off by default, `install_weak_deps=False` installs the same eleven packages, and `max_parallel_downloads=10` makes it *worse* — 37.3s against 6.0s. A fourth was wrong in a more interesting way: a research pass reported that Rocky ships `tsflags=nodocs` so `--nodocs` is a no-op. Rocky ships no such thing — its `dnf.conf` has five lines and `tsflags` is not among them; that is **Fedora's** default, attributed to the wrong distribution. The conclusion held and the reasoning did not, which is the failure mode that survives review. **What `--test-threads` bounds is not what costs.** It limits test *processes*, and the expensive thing is a container: eight test binaries were each free to start one, so `-j8` meant eight of something else. `.config/nextest.toml` puts the container scenarios in a group that means eight containers, and excludes the harness's own unit tests, which live in the same binaries and start nothing. `terminate-after` bounds a runaway at five minutes — generous on purpose, since openSUSE's sshd takes 111-122s to start under load and a tighter ceiling would kill scenarios that were going to pass. **Retries are deliberately absent**: nextest marks a recovered test FLAKY and counts it as a pass, and twice now this suite's flakiness has been a real defect — a wait that gave up before openSUSE's sshd answered, and a helper that read stdout as an exit code. Both were found because a test failed and *stayed* failed.

- **A container that never started must not be reported as a failed assertion about the code.** `exit_code_of` answered `-1` when no exit code came back, and the caller compared that against a number from `docs/cli.md` — so a Docker daemon too busy to start a container failed the exit-code contract test, which reads as the CLI having broken its promise to scripts and sends the reader to `main.rs` for a defect that is not there. It surfaced once in a full run and never in isolation, which is the shape of the fault rather than a coincidence: a suite that grew by eighty containers made a latent problem likely rather than creating one. The rule is the same one the missing-`diff` finding taught, one layer up: a helper that cannot ask its question must say so rather than return a value the assertion will interpret. Prefer a panic naming the image and both streams over a sentinel that is indistinguishable from an answer.

- **`Revert` is reachable only through the TUI, so that is where it is tested — driven by tmux, under systemd.** There is no `initd revert` subcommand by the same reasoning that keeps `ssh.allow-users` out of the CLI: a revert without a verification window is the operation the window exists to make safe. That leaves the interface as the only route, and rendering tests against a `TestBackend` cannot press keys. tmux is what makes the interface assertable — ratatui needs a real terminal, and the alternate screen means a pipe renders nothing while `script(1)` captures nothing readable once the program exits; tmux allocates the pty *and* dumps a live pane, without adding a crate to audit. It also has to run under systemd: without it `ssh.harden` writes the file, fails at `systemctl reload`, and the task ends `FAILED` — and a failed task offers nothing to keep or revert, so the verification window never opens. `tests/integration_tui.rs` reaches that window, presses `R`, and compares the restored file byte for byte with what preceded it.

- **Verifying `systemctl` needs systemd as PID 1, which needs `--cgroupns=host` as well as `--privileged`.** Without the second flag systemd exits 255 immediately and logs nothing, which reads like a broken image rather than a missing flag. `tests/integration_systemd.rs` is where `ssh.install` is observed to actually enable and start the right unit — `ssh.service` on Debian, `sshd.service` on Arch — a divergence that until then had only ever been checked against a mock. It is a separate binary that skips where the host will not grant those capabilities, because a rootless Docker has not found a bug. Assertions there compare `systemctl` output line by line: `is-active` answers `inactive` for a unit that does not exist, and `inactive` contains `active`, so a substring check passed against a container where the package had failed to install.

- **A failing `sshd -t` does not always mean the config is wrong.** Verified empirically on a fresh Arch container: validation fails with `no hostkeys available -- exiting` on a perfectly valid file, simply because host keys have not been generated. Treating every non-zero exit as "invalid config" would make the tool roll back good changes. The classification lives in `src/tasks/sshd_config.rs`; extend `NON_SYNTAX_FAILURES` when another such case appears. A mock would never have surfaced this — it only showed up in a real container.

- **User-facing text lives in the i18n catalogue, never in the code that raises it.** `Error` variants and TUI strings carry structured data; `src/i18n/` renders them in the locale resolved from the environment. The catalogue is a closed enum rendered by an exhaustive `match`, with no external dependency: a missing translation is a compile error rather than a runtime lookup miss, and adding a language means adding one module instead of touching every call site. `fluent` and `rust-i18n` were rejected — both resolve at runtime and pull in dependency trees to audit, for a catalogue this small. The claim was once broader than the code: it held for errors and consequences while the interface's own chrome — pill words, key-bar labels, the help overlay, the verification banner — was literals in the rendering code, so a second language would have produced a half-translated screen. All eight TUI modules go through the catalogue now, and so does the tasks' own narration: `report` takes a `Msg` rather than a string, which is what moved ninety lines of progress text out of `src/tasks/`. That claim had been true of the interface and false one layer down, which is the half-translated screen it was written to prevent — headings and errors in the operator's language above `installing wireguard-tools`. Rendering happens inside `report` because that is the one place every such line already passed through; a `Lang` threaded into `Task::run` would be a parameter fifty implementations carry and one forgets. Three kinds of string stay out because they are not words in a language: key glyphs (`Tab`, `↑ k`) and drawing symbols; the tasks' own ids, titles and descriptions, which reach the screen through `Task`; and what `report_verbatim` carries — the WireGuard client configuration a peer copies, where translating `[Interface]` would produce a file `wg-quick` cannot read. Modules that render every frame hold a resolved `Lang` rather than calling `from_env()` per message — an error reaches the catalogue rarely, a key bar is a dozen labels a frame. The migration was verified by dumping 736 rendered frames before and after and diffing them byte for byte, because a refactor that changes what is on screen is a regression no test in the suite was watching for. That harness was a throwaway and is not in the tree: it compared *this* tree against its own predecessor, which is a thing that only exists while the refactor is in progress. Anyone proposing another render-wide change builds it again rather than finding it.

- **Whether a locked password blocks a key depends on how the distribution *built* OpenSSH, not on how it is configured.** The `platform_locked_account()` check is compiled behind `!options.use_pam`: Debian and Arch build with PAM, so it is compiled out and a `!` hash admits a key; Alpine builds without it — `UsePAM` is not even a directive its `sshd -T` recognises — so the check runs and the same hash refuses everything. Found when an Alpine container refused a test account created by `adduser -D` despite it holding a valid key. `users.lock-root` uses expiry regardless, because that is the one mechanism meaning the same thing on all three.

- **A secret is written into a file whose mode is already right, never tightened afterwards.** `wireguard.install` wrote `wg0.conf` and then chmodded it, leaving the server's private key world-readable for as long as the two calls took. Brief, and long enough for any account on the box. It surfaced from `wg genkey` warning about the same mistake in a test's own redirect — not from a mock, which has no opinion about modes. The pattern to keep: create the file empty, set the mode, then write. An empty file discloses nothing.

- **Rendering reads the interface's state through `&App` from its own module, and the one place it writes is load-bearing.** `src/tui/render.rs` holds every `render_*` as a free function taking `&App`, the shape `search.rs` already used, which makes "drawing does not mutate" a property the compiler checks rather than a convention. It is not quite true, and the exceptions are the point: `render_tree` needs `&mut` because `frame.render_stateful_widget` is where ratatui *writes* the list's scroll offset, and the scrollbar drawn immediately after reads that offset back. Both orders compile and both draw a plausible scrollbar — the wrong one lags the thumb by a keypress — so the dependency is named in a comment at the call site, being invisible in the code. `Form::render` needs `&mut` for its own scroll state, which is the same reason `Mode` cannot carry payloads. `render_right` was declared `&mut self` and mutated nothing; the extraction is what surfaced it. Verified as a pure refactor by diffing 736 rendered frames across four families, twenty-three states and eight terminal sizes — and the harness was checked against a deliberately broken marker first, because a frame diff that cannot fail proves nothing. Like the i18n migration's, that harness compared the tree against its own predecessor and was not kept.

- **Static musl binaries, not glibc.** A binary linked against a recent glibc fails on older servers — exactly the machines an administration tool needs to reach. musl links statically and runs anywhere, which matters more here than the marginal performance difference.

- **The `curl | sh` installer verifies checksums before executing.** Piping a remote script into a shell runs unverified remote code, and this tool runs as root. Checksum verification against a published GitHub Release is the minimum mitigation; the release binaries are the source of truth, the install script is only a convenience wrapper. The check is exercised rather than assumed — `tests/integration_installer.rs` serves a release and replaces the binary after its digest was computed, so a script that verified nothing would fail there. What it does *not* defend against is stated in the script and the release notes: anyone able to publish a release writes both the binary and its digest. **Signing was considered and declined.** It would close exactly that gap, and nothing else — a signature only matters if this repository's publish permissions are compromised. The cost falls on every install, and it is not the same cost everywhere: `minisign` is packaged and preinstalled on none of the five families, and on RHEL it is not in the base repositories at all — measured on `rockylinux:9`, where BaseOS, AppStream and Extras carry no such package and it installs only once EPEL, a third-party repository, has been enabled. So requiring it turns the one-line bootstrap into three commands on a freshly provisioned Debian or Arch box, and into "add a third-party repository first" on RHEL, which is a strange thing for a script whose purpose is to verify provenance to ask of someone. Degrading gracefully instead — verify the signature where the tool exists, warn where it does not — was rejected as worse than either: a warning nobody can act on trains people to ignore it.

## WHAT — Deliberately not built yet

Absent by decision, not oversight. The design admits each without rework:

- **Remote execution over SSH.** The `Executor` trait exists precisely so this becomes a second implementation; `LocalExecutor` is the only one today.
- **General package administration.** Installing arbitrary packages is a
  different shape of task from the ones here: every task in the tree today
  names a capability the backend resolves, and a free-text package name has no
  backend to resolve it against.
- **A second WireGuard interface.** `wg0` is fixed rather than asked for,
  because a second interface is a different topology and not a different value.

## HOW — Conventions
Detailed conventions live in `~/.claude/rules/` — global Claude Code config, outside this repository, applied to every project (those with a `paths:` field load only for matching files; the rest load every session). `docs/conventions.md` is the portable mirror for tools that don't run Claude Code:
- Code quality → `~/.claude/rules/code-quality.md` (loads for source files via `paths:`)
- Security → `~/.claude/rules/security.md`
- Workflow → `~/.claude/rules/workflow.md`
- AI collaboration → `~/.claude/rules/ai-collaboration.md`

**Minimum rules that apply everywhere:**
- Follow the existing style in neighboring files before inventing new patterns.
- Strict typing wherever the language allows it.
- Explicit error handling, no swallowed errors.
- Tests for new logic (at minimum: happy path + 1 edge case).
- Atomic commits: one logical change per commit.
- `CHANGELOG.md` updated with every relevant change (Keep a Changelog format).

## Don't
- DO NOT branch on the distro inside a task. If a task needs `match distro`, the missing abstraction belongs in a domain trait — put it there instead.
- DO NOT call `std::process::Command` outside `src/exec/`. Every command goes through `Executor`, or the future SSH implementation becomes a full refactor.
- DO NOT use `unwrap()` / `expect()` / `panic!` in production paths. This runs as root on someone's server: a panic mid-operation can leave the system half-configured. Propagate errors and report them in the TUI.
- DO NOT hardcode paths to binaries (`/usr/bin/apt`). They differ across distros — resolve via `PATH`.
- DO NOT assume a package name is the same across distros (`docker.io` vs `docker` vs `docker-ce`). Names belong in the per-family backend.
- DO NOT run destructive operations without an explicit confirmation step in the TUI.
- DO NOT add dependencies without explicit confirmation — every new dep is audited (`cargo deny check`).
- DO NOT mix refactor with feature in the same commit — it complicates rollback.
- DO NOT use `git commit --amend` without explicit user request — always create a new commit.
- DO NOT auto-sign commits with `Co-Authored-By` unless explicitly requested.

## Workflow
- Changes touching >3 files: **plan mode first** (use `/plan-feature`).
- Before declaring a task done: **always** `/verify`.
- Before each commit: `/changes` to review the diff, then `/commit` (it updates CHANGELOG.md).
- When opening a new session in an ongoing project: `/resume-context`.
- When I correct a systematic mistake: use `/compound` so it does not happen again.
- Before merging anything that touches I/O, auth, or deps: `/security-review`.
- Branch model: feature branches by default. The `guard-push-main` hook blocks direct pushes to main/master. If this project intentionally lives on main (solo project, prototype, scratch repo), add `"allowPushToMain": true` to `.claude/settings.local.json` (see `settings.local.json.example`). Force pushes stay blocked regardless.

## Portable docs — `docs/`
- `docs/` is the **portable contract** of this project, split across self-maintained files: `cli.md` (the programmatic contract — subcommands, arguments, exit codes; this was `backend.md`, renamed because `initd` exposes no network API), `ui.md` (the visual contract of the TUI — panels, keys, style roles), `user-stories.md` (the behavioral contract — everything the user can do, interface-agnostic), and `conventions.md` (how to write the code — a portable mirror of `~/.claude/rules/` for tools that don't run Claude Code). It exists so that tools or contributors who can only see one slice of the repo (Xcode workspace, embedded subdir, sandboxed editor) can still build the right mental model and follow the same conventions. Each file carries its own maintenance rules in its header, so it stays usable even where `/update-docs` is not available. See `docs/README.md`.
- **Coverage over depth.** Every capability the system exposes must appear in `docs/`, even if as a one-liner. A reader of `docs/` should be able to answer *"what can this system do?"* without opening the source. Detail per entry can be shallow; the list of entries must be exhaustive.
- **Mandatory step at task close.** Before declaring any task done, ask yourself: *"did this change a contract another part of the system relies on?"* If yes, run `/update-docs` **before** `/commit`. This is non-negotiable — desynced docs are worse than no docs.
- **What counts as a contract change** (update required):
  - `cli.md`: added/removed/renamed subcommand or task id, changed arguments, changed output, changed exit codes, changed error semantics.
  - `ui.md`: added/removed/renamed panel, changed what a panel does, changed a key binding, or added/rebound a style role.
  - `user-stories.md`: the user can now do something new, can no longer do it, or achieves it differently (write it interface-agnostic; add a TUI/CLI exception only if the two genuinely differ).
  - Any new file under `docs/` when a new contract producer/consumer appears.
- **What does NOT count** (skip — do not pollute docs with noise):
  - Internal refactors, renamed private helpers, logging, formatting, dependency bumps with no behavior change.
  - Tests, build/CI config, comments.
  - Bug fixes that restore documented behavior rather than change it.
- **If unsure, invoke `/update-docs` anyway.** The skill detects "nothing to update" and exits — false positives cost nothing, false negatives leave stale docs.
